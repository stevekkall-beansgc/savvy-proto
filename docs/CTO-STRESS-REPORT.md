# Reconciliation stress and reporting review

2026-11-13. This is a synthetic local rehearsal, not a production load test or an accounting close.

## Measured results

`docker compose run --rm -e RAILS_ENV=test api bundle exec ruby test/reconciliation_stress_test.rb` passed **11 tests and 167 assertions**, seed 48123, in 1.971 seconds. Four workers race 20 identical idempotent retries; four applications contend for a bounded receipt; two bank batches contend for the same receipt; ten freeze/write and ten application/receipt-reversal races require either coherent serialization or an explicit rejection. Tests also cover one-time full reversal, idempotency conflicts, injected failure after evidence creation with transactional rollback, unsupported status, invalid date and decimal, cross-customer or missing scope, source ID conflict, forbidden writes, and GraphQL reads for all five roles. The database pool is five and the harness uses at most four workers. The test setup deletes demo rows in the explicitly checked `advisor_economics_synthetic_test` database; never run it against retained demo history, and coordinate exclusive access to the shared test database.

The canonical populated fixture was run separately in that test database, followed by a dbt build against test-only `raw_demo` views and a profile pointing to that database. Before receipt correction, the API measured two invoices totaling 200000 minor units, applied 160000 and open 40000; the entity batch measured gross 160000, fee 3000 and net 157000. After source receipt reversal those independent application and batch amounts persisted and two explicit conflicts were reported. The dbt build passed **55 of 55** model and data-test steps with the same invoice and batch totals and two membership rows. The final populated run includes the subsequent entity-wide unknown-axis exceptions; no accounting posting or recognized revenue was implied.

Run `./scripts/reconciliation-check.sh` from the project root to repeat the populated reporting rehearsal. It verifies the configured Rails database is the disposable test database before clearing demo rows, generates a test-only bootstrap and dbt profile in a temporary directory, isolates dbt target and log paths, runs all models and tests, and independently asserts the canonical totals, two membership rows and two conflict rows. The latest complete run passed all 55 dbt steps, including 41 data tests, with these assertions. Its output is retained in `artifacts/cto-readiness/reconciliation-check.log`. Coordinate exclusive test-database access before running it; the test database is reset by the fixture. The retained demo database is not used by this check.

## Scope and limitations

The reporting marts preserve application history and reversal evidence, current invoice balances with unknown distinguished from evidenced zero, entity-grain batch amounts, and a separate membership bridge with no additive batch measures. Source receipt revisions are captured and conflicting corrections are surfaced, rather than silently removing independently recorded evidence. Reporting represents current evidence, not a frozen historical warehouse publication; missing-bank and recognition exception rows are entity-wide, while the application review provides period-specific results. Do not sum batch amounts after joining to membership or infer customer net deposits, accounting postings, or revenue recognition.

This exercise tests bounded local races and an injected operation-write failure, not sustained throughput, crash recovery under arbitrary process termination, distributed multi-instance isolation, provider integrations, or production authorization. A separate restore rehearsal checks the retained synthetic database without replacing it. Production controls and policy decisions remain outside this prototype.
