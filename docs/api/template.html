Implemented API

The application uses GraphQL. OpenAPI describes its HTTP transport; the GraphQL schema defines its operations. All examples use fictional records. The reference displays examples and schemas without sending requests or collecting credentials.

HTTP endpoints

MethodPathAvailability
POST/api/graphqlPublic demo proxy at https://savvy-proto.beanshop.top. Fresh clones use http://127.0.0.1:3100.
POST/graphqlDirect Rails API on loopback. Port 3101 for fresh clones, or 3108/3109 on the hosting device.
GET/healthRails service metadata on the same loopback API port.

Send an application/json body with query, optional variables and optional operationName. A single endpoint carries the named queries and mutations below.

The proxy accepts at most 1,048,576 characters; Rails accepts at most 1,048,576 UTF-8 body bytes and 50,000 query bytes. GraphQL depth is bounded at 10 and complexity at 150. The hosted frontend enforces an origin allowlist.

Identity & permissions

Read prepared records in the hosted demo without signing in. To make changes, choose Start your own demo in the working app. The browser sends the HTTP-only savvy_demo_session cookie for that isolated workspace. X-Demo-Role selects a simulated role and defaults to operator. The demo uses synthetic identity and records.

Simulated roleRelevant scope
advisor / riaClient reads for their own case. They cannot elevate access by requesting an internal audience.
operatorInternal reads, draft/compare/publish/assign/evaluate household policies. Publication requires the exact current Legal and Finance approvals.
legalPermitted internal reads and independent policy review.
financePermitted finance reads, independent policy/event review and scoped cash-association commands.
auditorPermitted internal read projections; command-specific guards still apply.

Tenant and entity scope are supplied by the server. Each command also enforces its own role, relationship, evidence and period rules. Read visibility does not grant write permission.

GraphQL operations

Open an operation for its arguments and request shape. Fields returning JSON have operation-specific projections; the transport does not promise a universal invoice or statement response shape.

Command inputs and examples

Household policies follow draft → compare → Legal/Finance reviews → publish → assign → evaluate. Publication and assignment are separate decisions. Evaluation retains a result; a changed billed period flags a correction while preserving the original invoice.

One-time requests enter as versioned events. Finance review is separate from confirmed payment evidence. Cash association links existing evidence to an invoice; recognition needs its own supplied accounting outcome.

Separate fixture periods

Household policy examples use February 2027. The baseline one-time event example uses September 2026. Finance association examples use their separate 2027 timing records. IDs, policies and service intervals must belong to the same supported case and namespace.

Data, retries and errors

  • Money is an exact decimal integer string in minor units with a currency. Rates use exact rational strings. Unknown values remain null.
  • Service end dates are exclusive in storage/API fields. The UI displays the inclusive last day.
  • Pagination uses limit and offset. Household workspace pages are a deterministic slice across its section lists, default 20 and maximum 100.
  • Each write takes idempotencyKey: 1–100 letters, digits, underscores or hyphens. The same actor/operation/key and input replays its result; changed input yields IDEMPOTENCY_CONFLICT.
  • Check HTTP status, top-level errors and data.<command>.errors. HTTP 200 can contain a rejected command.
  • Use the returned identity, revision and hash for later reviews or replacements. An approval bound to stale evidence cannot authorize a changed request.

Validation, scope, review, stale evidence, period locks and source conflicts are distinct failures. A command response does not establish payment execution, a signed agreement or live accounting posting.

MCP / WebMCP

This API is the application foundation for future agent tools. An MCP server and browser WebMCP registration are not implemented yet. Those additions need explicit tool schemas, real authenticated identity and account scopes, protocol/client compatibility tests and the same existing review boundaries.

Both adapters would call the existing Rails services. The billing engine, API-driven policies and Savvy-owned billing records remain shared.
